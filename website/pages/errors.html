Errors

How Sigma reports problems, and how your program can catch and raise its own errors.

Two kinds of errors

  • Compile errors are found before the program runs: typos, wrong number of arguments, using a variable that doesn't exist, changing a lock constant. The program doesn't start until they're fixed.
  • Runtime errors happen while the program runs: reading past the end of a list, doing math on text, dividing by zero, opening a file that isn't there. You can catch these.

Reading a compile error

cook area(w, h) { serve w * h }
yap(area(3))

error: 'area' takes 2 arguments, but got 1
 --> main.sgm:2:5
  |
2 | yap(area(3))
  |     ^^^^
  = hint: it's defined as  cook area(w, h)

The first line says what's wrong. The arrow line gives file:line:column. Then comes the line of code with carets under the problem, and sometimes a hint with a suggested fix.

Reading a runtime error

price: "1200"
yap(price * 2)

error: can't do math with this: expected a num, got str "1200"
  --> main.sgm:2

An uncaught runtime error prints the message and the line, and stops the program with exit code 1. (Here the fix is num(price) * 2.)

Catching errors: yolo and oops

Put risky code in a yolo block. If anything inside fails, Sigma jumps to the oops block, with the error in the variable you name:

yolo {
    scores: [10, 20]
    yap(scores[5])
    yap("this line never runs")
} oops e {
    yap("caught: {e}")
}
yap("the program keeps going")

caught: index 5 is out of range (the list has 2 items)
the program keeps going

Errors pass up through function calls until a yolo catches them, so you can put one yolo around a large piece of work.

The oops part is optional. Without it, errors in the block are ignored:

yolo { yap(1 / 0) }
yap("still running")

still running
Use it sparingly

Ignoring errors hides bugs. A yolo without oops is best for things that genuinely don't matter, like a cleanup step.

Raising errors: yeet

yeet raises an error with any value. It's usually a message string:

cook withdraw(balance, amount) {
    fr amount > balance { yeet "not enough money (balance is {balance})" }
    serve balance - amount
}

yolo {
    yap(withdraw(100, 30))
    yap(withdraw(100, 500))
} oops e {
    yap("failed: {e}")
}

70
failed: not enough money (balance is 100)

You can also yeet a map to attach details, and check them in oops:

yolo {
    yeet {code: 404, message: "user not found"}
} oops e {
    fr type(e) == "map" and e.code == 404 { yap("404:", e.message) }
}

404: user not found

Errors raised by Sigma itself (like a bad index) arrive in oops as strings.

Passing an error on

Inside oops, yeet again to let a caller deal with it, perhaps with more context:

cook load_config(path) {
    yolo {
        serve read_file(path)
    } oops e {
        yeet "couldn't load config: {e}"
    }
}

yolo { load_config("missing.txt") } oops e { yap(e) }

couldn't load config: can't read file 'missing.txt': No such file or directory

Assertions: vibecheck

vibecheck(condition, message) raises an error when the condition is falsy. Use it to state what must be true, both in programs and in tests.

cook set_age(age) {
    vibecheck(type(age) == "num", "age must be a number")
    vibecheck(age >= 0, "age can't be negative, got {age}")
    serve age
}
yolo { set_age(-3) } oops e { yap(e) }

vibe check failed: age can't be negative, got -3

Validating input

Since num gives nil for bad text, you can check input without catching anything:

grind {
    answer: num(ask("How many? "))
    fr answer != nil { dip }
    yap("please type a number")
}
yap("ok, {answer}")

How many? please type a number
How many? ok, 12

Exit codes

An uncaught error exits with status 1. Use exit(code) to end the program yourself with any status. A status of 0 means success to the shell and to tools like make and CI systems.

fr len(args()) == 0 {
    yap("usage: tool ")
    exit(2)
}
