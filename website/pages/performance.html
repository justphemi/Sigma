Performance

How Sigma turns dynamic-looking code into fast native programs, and how to keep your code on the fast path.

How a program runs

app.sgm -> lexer -> parser -> checks and type inference -> C code -> clang or gcc -> native program
  1. Sigma reads your file and every file it yoinks, and checks the whole program for errors.
  2. It works out the type of every variable, parameter and function result it can.
  3. It writes a C program and compiles it with your system's C compiler at -O2.
  4. The executable is saved in a cache (~/.cache/sigma), keyed by a fingerprint of the code and compiler. The next run of unchanged code skips straight to running it.

Type inference

Sigma is dynamically typed: a variable can hold anything. But most variables only ever hold one kind of value. When the compiler can prove a variable is always a number (or always a boolean), it stores it as a raw machine value instead of a general "any value" box.

total: 0
grind i in 0..1_000_000 {
    total += i
}

Here total and i are always numbers, so this compiles to the same C loop you'd write by hand:

for (double v_i = 0; v_i < 1000000; v_i++) v_total = v_total + v_i;

This works across functions too. In fib(n), if every call passes a number, n becomes a raw number and so does the result. You can see what the compiler produced with sig emit file.sgm.

Everything else

Values that can be several types, plus all strings, lists and maps, use a compact 16-byte tagged value with fast paths for the common cases:

  • memory comes from a fast bump allocator,
  • maps are hash tables that cache each string's hash,
  • s += text appends in place when it can, so building strings in a loop isn't slow,
  • list indexing and number formatting have inline fast paths.

Writing fast Sigma

Keep a variable to one type

A variable that is sometimes a number and sometimes nil or a string has to use the general representation everywhere. Use a number as the "nothing yet" value when a number is expected:

nums: [3, 9, 4]

-- slower: best is nil, then a number
best: nil
grind x in nums { fr best == nil or x > best { best: x } }

-- faster: best is always a number
best_n: -1
grind x in nums { fr x > best_n { best_n: x } }

Do heavy work inside functions

Local variables in a function are the easiest for the C compiler to keep in processor registers. Top-level variables that functions also use become globals, which are slightly slower in tight loops.

Prefer ranges for counting loops

grind i in 0..n compiles to a plain C for loop. It doesn't build a list.

Build lists once

push is cheap. insert(0, x) and del(0) move every other item, so avoid them on large lists in a loop.

Use sig build for repeated runs

Cached runs start fast, but a built executable skips even the cache lookup. For a tool that runs thousands of times from a script, build it.

Memory

Sigma doesn't have a garbage collector yet. Memory is allocated quickly and never freed while the program runs, then released all at once when it exits. Short-lived programs (scripts, tools, data processing, puzzles) don't notice. A program that runs for a long time and keeps creating new strings, lists or maps will keep growing, so long-running servers aren't a good fit for now.
